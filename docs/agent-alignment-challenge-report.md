# Agent Instruction Alignment — Challenge Report

**Created / last verified:** 2026-07-26 · **Slug:** `agent-alignment`
**Plan of record:** `docs/agent-alignment-roadmap.md`

Four adversarial reviewers ran against the five design lanes before the plan of record was written. **All four returned a verdict of `blocker`.** This file records what they found, what changed, and what did not — because a plan that absorbs criticism silently is indistinguishable from one that ignored it.

**Reviewers.** (S) safety-regression challenger · (P) project-law compliance challenger · (Q) sequencing-and-collision challenger · (F) falsifiability challenger.

**Headline outcome.** 8 blockers and 21 majors were raised. **26 were CONFIRMED and applied.** 2 were **CONFIRMED and consciously ACCEPTED** rather than fixed, with reasons below. 1 was **UNFOUNDED**. 4 were **PARTLY FOUNDED** — the defect was real but the reviewer's diagnosis or fix was wrong, and the plan applies a different remedy. The single most consequential outcome is that **one lane's proposed "fix" would have broken both live safety guards**, and it was caught by re-measuring rather than by reasoning.

---

## §1 The four findings that changed the plan's shape, not just its details

These are recorded first because they are the ones a reader should check for.

### C-1 — CONFIRMED, and the reviewer's own diagnosis needed correcting too · (S, blocker)

**The finding.** One design lane proposed removing `${CLAUDE_PROJECT_DIR}` from the hook command strings in favour of in-script `git rev-parse` resolution, on the stated grounds that 2.1.85 does not support the variable. Reviewer S reproduced that `cd src && bash ./.claude/hooks/block-secrets.sh` returns **exit 127** — and 127 is not 2, so per the plan's own established fact both safety guards are **silently absent for any session whose cwd is not the repo root.**

**Re-verified here:** yes, the 127 behaviour and the `set -e` / exit-code semantics. And the design lane's premise is **false**: the installed 2.1.85 bundle *does* inject `CLAUDE_PROJECT_DIR` into the hook environment (a sibling lane recorded the correct fact; the plan contradicted itself and was about to act on the wrong half).

**Why this was nearly a data-loss change.** In-script resolution cannot help, because the failure happens **before the script runs**. So the proposed fix would have replaced a working absolute resolution with a cwd-dependent one that fails **open** — while the L2/Codex design actively encourages launching sessions from subdirectories.

**Applied.** P5 now **keeps** `${CLAUDE_PROJECT_DIR}` and adds a **fail-closed wrapper**: resolve the variable, fall back to `git rev-parse --show-toplevel`, and if the guard is still unresolvable **print a reason to stderr and exit 2**. `.gitattributes` gains `*.sh text eol=lf` in the same commit (a CRLF parse break is also exit-not-2). The incorrect `${CLAUDE_PROJECT_DIR}` row is deleted from P0's evidence file and replaced with the measured bundle evidence. Roadmap §2 records the correction on the record.

### C-2 — CONFIRMED · (S, blocker) — the plan's riskiest single commit was split in two

**The finding.** One lane introduced the `@AGENTS.md` import **and** deleted `CLAUDE.md`'s non-negotiables in the same phase, making a never-before-used mechanism the sole carrier of all 12 rules. No phase in any lane verified that a root `@`-import survives `/compact`. The bundle's `InstructionsLoaded` enum treats `include` as a load reason **distinct** from `session_start` and `compact`, which means imported files are tracked separately at exactly the boundary where the plan claimed safety. A cold-session canary cannot detect this because it never compacts.

**Re-verified here:** there is no `@`-import anywhere in `CLAUDE.md` or `AGENTS.md` today, so the mechanism is genuinely unproven in this repo.

**Applied.** The phase is split: **P2** adds the import and **keeps** the duplicate; **P3** deletes the duplicate **only after a post-compact canary passes** in a session with real work in it. The failure branch is written into the plan as a legitimate outcome: *if the import does not survive compaction, the non-negotiables stay in `CLAUDE.md` permanently, the L0 core becomes Codex-only, and that is recorded rather than forced.* The rollback order is fixed (revert P3 before P1). The same post-compact assertion was added to P9's precondition.

### C-3 — CONFIRMED, and it is a live security gap nobody had noticed · (S, blocker)

**The finding.** Every lane cited `.claude/settings.json`'s `permissions.deny` as the enforcement baseline, but its destructive entries are keyed to server **aliases** (`mcp__UPR_MCP__*`, `mcp__github__*`, `mcp__Gusto__*`) that do not match the live server ids.

**Re-verified here:** yes. The deny list contains exactly those 13 alias-keyed entries; the live servers in session are `mcp__c6f3f344-…` (UPR) and `mcp__1cd66b34-…` (Supabase); `.claude/settings.local.json` uses three *further* aliases including hash forms, which is direct evidence of drift across re-registrations; and there is no `.mcp.json` in the repo to pin names.

**Consequence.** `upr_sql` — a **free-form SQL tool on the shared production project** — plus `upr_update`, `upr_delete`, `upr_insert`, `upr_upsert`, `upr_rpc`, `github_commit_file`, `github_merge_pr` and `github_request` (raw GitHub API passthrough that can commit to `main` or merge a PR, bypassing git entirely) are **live with no matching deny.** The existing PreToolUse **regex** matcher does survive id churn but covers only `apply_migration` and `execute_sql`.

**Applied.** P4 now extends the regex matcher to `mcp__.*__(apply_migration|execute_sql|upr_sql|upr_update|upr_delete|upr_insert|upr_upsert)` and adds a second regex matcher for the three GitHub write tools routed to P6's publish guard. P0 gains a probe of a denied-by-alias tool with the observed result pasted. This became **owner decision #7**, which did not exist in any design lane. P6's parity table must state which gates are regex-backed and which are name-keyed-and-unverified.

### C-4 — CONFIRMED · (Q, blocker) — the mechanically enforced counter no lane had named

**The finding.** Seven phases across four lanes change a tracked entrypoint count, and every one named only `docs/tooling-governance.md` §1's **prose** stamp. The actual gate is `.claude/tooling-governance.json` → `trackedInventory`, read via `git ls-files` and compared by **exact equality**. Each of those phases also listed "`npm run validate:tooling` exits 0" as an acceptance criterion — **so each failed its own gate.** Two lanes also asserted contradictory expected values for the same counter, and one named `admin-mobile-phase-reviewer.md` in `governedEntrypoints` while another deleted it.

**Re-verified here:** `.claude/tooling-governance.json` exists with `trackedInventory = {skills: 24, agents: 15, rules: 23, hooks: 2}`, `asOf 2026-07-23`; `npm run validate:tooling` is currently green; and the `governedEntrypoints` array does name that agent by path.

**Applied.** Roadmap §4 invariant 1 names the JSON as the file of record, publishes a **sequenced arithmetic ledger** giving the exact expected 4-tuple after each phase, and requires both the JSON and the prose stamp to change in the same commit. P14's conditional deletion now also removes the `governedEntrypoints` row, and its conditional rename repoints all four paths **plus** the frontmatter `name` fields. The manifest DRAFT gives the counter one owner per change.

## §4 CONSCIOUSLY ACCEPTED — real findings the plan does NOT fix, with reasons

These are the two findings judged correct that the plan deliberately leaves open. Recording them is the point; a plan that quietly dropped them would be worse than one that never heard them.

### A-1 — Subagent hook coverage is untested, and the plan ships without knowing the answer · (S-9, minor)

**The finding, and it is correct.** No phase in any lane tested whether PreToolUse hooks fire for tool calls made by a **subagent**. The entire publish gate and both existing safety gates rest on PreToolUse. `impeccable-manual-edit-applier` is the one write-capable Claude subagent, its `tools:` list includes `Bash`, and `Bash(git push *)` is pre-approved in the tracked local settings — so if hooks do not fire in subagents, that subagent is an un-gated publish **and** un-gated secret-write path.

**What the plan does.** P6 adds the probe (dispatch a subagent instructed to run `git push origin main --dry-run`; require the refusal **plus** the hook's sentinel line), and P11 makes the `Bash` capability conditional on the result.

**What it does NOT do, and why that is accepted.** The plan does **not** pre-emptively remove `Bash` from that subagent, and it does **not** gate any earlier phase on the probe's outcome. Reason: removing a documented, intentional capability on the strength of an untested hypothesis would break the one write-capable subagent the repo relies on for applying design fixes, and the alternative — blocking Waves 1–4 on a single probe — is disproportionate to a risk that (a) requires a session to route a publish through a subagent, which nothing currently does, and (b) is already covered on the `main` path by the enumerated denies P4 adds, which are evaluated per tool call regardless of who made it. **The residual is disclosed:** until P6's probe runs, the plan does not claim subagent-originated tool calls are gated.

### A-2 — Nothing in this plan closes CAP-SEC-001, including the cleartext credential · (S/P/F, all raised it)

**The finding, and it is correct.** The tracked `.claude/settings.local.json` pre-approves `apply_migration`, `execute_sql`, `git add`, `git commit`, `git push` and `gh pr`, has no `deny` key, and one allow entry embeds a **literal live Encircle API bearer token in cleartext**. `block-destructive-sql.sh` is the sole surviving gate on the apply path. The validator waiver expires **2026-08-06**.

**What the plan does.** Records the full inventory in three places, names the residual mechanism precisely, labels publication to non-`main` refs PROSE-ONLY in the parity table, and raises it as owner decision #6 with a recommendation (untrack **and** deny by name, plus rotate the credential).

**What it does NOT do, and why that is accepted.** No phase edits that file. Reasons, in order: (1) it is an **already-recorded owner gate** — `tooling-governance.md` §6 assigns the rotation, history review, sanitisation and local-approval reset to the owner explicitly, and a plan that quietly did part of it would blur an accountability line the owner drew on purpose; (2) rotating a credential is a **provider action**, which this plan is categorically forbidden from taking; (3) `git rm --cached` on a tracked settings file changes every contributor's local approval state, which is a coordination act, not a docs change. **The residual is disclosed and it is the largest one in the plan:** until #6 is answered, one PreToolUse hook stands between a standing pre-approval and shared production, and P12's probe 4 may reveal the Codex-side twin of that hook never fires at all.

## §7 What resisted maximum parallelism — the honest ledger

① **L2 must be authored twice.** Codex has no conditional-markdown mechanism at all, so the depth tier is structurally asymmetric.
② **Cheap-at-startup and survives-compaction are mutually exclusive in Claude.** So a slice of the 210.8 KB — `database-standard.md`'s 9,342 B — can never be moved, by design rather than by omission.
③ **The Codex half is unmeasurable.** No `InstructionsLoaded`, no `/context`, no truncation warning. The migration is **provable** on one side and only **plausible** on the other, and every artifact says so rather than claiming parity.
④ **The root instruction pair is one seam and cannot be parallelised.** Two phases wanted to add content to it and are forbidden from doing so; they supply text for its owner to install.
⑤ **Wave 1 is strictly serial** (P1 → P2 → P3), because each phase's safety argument depends on the previous one's proof.
⑥ **Enforcement parity is unreachable on this platform** without an owner WSL2 decision, and the asymmetry is inverted from intuition.
⑦ **Four gates are externally owned** — the Codex CLI is not on PATH here, so E1, E2, the walk test, the review probe and the branch-protection confirmation are all owner-run.
⑧ **The largest remaining consolidation is deliberately not attempted.** Collapsing the five initiative phase-reviewers would edit live inter-session contracts.
⑨ **Two owner-approved 2026-07-26 items plausibly outrank this initiative** for review bandwidth — the anon-write closure tranche (a) and the participant-scoping build. This plan is docs/config-only, ships zero migrations and touches no live state, so it can run in parallel with both. **It does not claim precedence.**
