# Domain: Documents & Storage

Job files (photos, notes, PDFs, generated reports), the customer-facing e-signature pipeline (sign_requests + token-gated public RPCs + SignPage/submit-esign worker), editable legal document templates, and the two Storage buckets (`job-files` public, `message-attachments` private/worker-only). The domain is heavily used and functionally healthy — 3 of 4 tables and all 12 RPCs are live, job_documents alone shows 72k seq scans — but its authorization layer is the weakest in the audit set: every live policy on the public-schema tables is either always-true or role-exclusion-only, the TO-public CRM-partner policy family silently re-opens **anonymous full CRUD on job_documents**, the public bucket exposes signed legal PDFs on unauthenticated URLs, and the DB never enforces e-sign status/expiry on retrieval (client/worker band-aid, audit-documented). One table (document_requests), two columns, and one policy are dead.

## Structural problems (ranked, worst first)

1. **Anonymous full CRUD on job_documents via the TO-public CRM-partner policies — sev 5.** `job_documents_select/insert/update/delete` (from 20260701_crm_partner_rls_non_crm_tables.sql) are `TO public` with predicate `NOT is_crm_partner(auth.uid())`; `is_crm_partner(NULL)` returns false (plain EXISTS), so the predicate passes for the anon role, and grants.json shows anon retains full table privileges. The P3 anon-policy closure re-scoped only the `anon_*`-named family to authenticated and left this family in place, silently neutralizing the closure for this table: a browser with only the publishable key can select, insert, update, and delete job_documents rows. This is table CRUD, well beyond the §2 allowlist's "public job-file READ" intent. Fix shape: add `TO authenticated` to the four policies (or fold the exclusion into the authenticated family).
2. **job-files bucket: public objects + anonymous listing + unscoped staff delete — sev 4.** Bucket `public: true` (prod-buckets.json) means every object — including signed legal PDFs written by complete_sign_request — is fetchable unauthenticated; `job_files_select` (TO public) + redundant `anon_read_job_files` additionally permit anonymous *listing* of the entire bucket via the Storage API; `job_files_authenticated_delete` lets any staff session delete any object (a signed contract's evidentiary PDF is deletable by any employee, and JobPage's cancel flow already deletes signed files). Deliberately deferred to P8 (private bucket + signed URLs, per 20260708_dbf_p2_storage_lockdown.sql), but P8 is unshipped and the exposure is live.
3. **E-sign enforcement lives above the database — sev 4.** `get_sign_request_by_token` (granted to anon AND bare PUBLIC) does token-only lookup with no status/expires_at predicate and returns job PII; expiry/status are enforced only in SignPage.jsx:199-201 (client) and submit-esign.js:171-173 (worker). `complete_sign_request` checks `status='pending'` but not `expires_at`, and is executable by any authenticated session — an internal caller can complete an expired request or fetch any historical signed request's PII given its token. The audit already documents this band-aid boundary; the DB-side fix (predicate in the RPCs + revoke PUBLIC) is small and contract-compatible.
4. **Authorization theater on the domain's public-schema tables — sev 3.** Every live policy is always-true (`sign_requests` ×4, `document_templates` ×2, `job_documents` anon_* ×4) or exclusion-only (#1); duplicate permissive generations coexist on both job_documents (2 families) and sign_requests (3 single-cmd policies subsumed by an ALL policy), and names lie (`anon_*` policies scoped TO authenticated). Combined with no-caller-check DEFINER RPCs, any authenticated user of any role can cancel/rewrite sign requests and edit legal template text (`upsert_document_template`). Consolidate to one honest policy set per table and role-gate template writes.
5. **document_requests is a dead table — sev 2.** Never wired to any UI/worker/RPC; 0 rows, 0 writes ever recorded; only merge_jobs housekeeping references it. Candidate for a reviewed destructive drop (table + policy + FKs), or for the owner to revive the request-from-customer workflow deliberately.
6. **Dead/orphan columns from half-shipped features — sev 1.** `job_documents.encircle_media_id` (Encircle media import never linked to job Files; carries a unique index that costs writes), `sign_requests.link_clicked_at` (click-tracking half never shipped; open-tracking half did), `job_documents.esign_status` (write-only mirror of sign_requests.status, never read). All droppable in a reviewed change; none is load-bearing.

## Open questions for the owner

1. **Document requests:** was "request a document from the customer and track when it arrives" (document_requests) a workflow you still want? It was built empty and never wired — drop it, or should it be finished?
2. **Encircle media:** should Encircle claim photos ever import into a job's Files tab (that's what `job_documents.encircle_media_id` was for)? The Encircle workers exist but never link media to job documents — is that integration still planned?
3. **E-sign click tracking:** email open tracking shipped; link click tracking (`link_clicked_at`) never did. Do you want click tracking, or should the column go?
4. **Template editing authority:** today any logged-in employee (any role) can rewrite the legal text of Work Authorizations / Reconstruction Agreements via Settings → Templates. Who should actually be allowed to?
5. **Public signed contracts:** signed legal PDFs currently sit on public URLs (anyone with the link, no login, forever) until the signed-URL migration (P8) ships. Is that acceptable short-term, and what priority should P8 get?
6. **Sign-request lifetime:** links expire at 30 days by convention, but the database itself never refuses an expired token — only the signing page and worker do. Any business reason a staff member should be able to complete an expired request, or should the database enforce expiry?
