# Executive verdict

READINESS  37 findings: 7 P0 release blockers, 24 P1 high-priority defects, and 6 P2 polish items. The PWA remains the visual/behavioral regression control—not a codebase to replace.

Do not split the product into an unrelated second application. Keep shared domain logic, authorization, data access, routes, and design tokens; introduce narrow native adapters for keyboard, status/safe areas, pickers, intents, notifications, haptics, lifecycle, and platform motion.

The most visible defects are systemic rather than page-by-page styling accidents: multiple owners currently compete for keyboard geometry, safe areas, status-bar appearance, scroll restoration, route motion, and foreground refresh.

A controlled warm-resume test disproved one suspected failure: the long job-note draft, scroll anchor, and keyboard were pixel-stable after resume. The visible problem is the abrupt privacy-cover handoff. Saving that same note separately did reproduce a real page-collapse spinner and scroll clamp.

## Release, trust, authorization, and qualification

### REL-01 — Apple team identifiers and Associated Domains are stale

P0  Evidence: Source-confirmed release blocker  ·  Routes: Universal Links; Password AutoFill; signing

Finding. The Xcode project and AASA file still use the old Personal Team identifier P93U4Z4DJB, while the newly approved paid team is H6ZUT739T9. The webcredentials entry also names com.utahpros.mobile rather than a valid application identifier.

Why it happens. Signing and association artifacts were not regenerated after Developer Program approval. Existing unit tests currently assert the stale values, so they would preserve the defect.

Recommended fix. Select the paid team in Xcode/App Store Connect, update signing settings and entitlements, publish a correct AASA containing the paid-team appID, fix webcredentials, then update tests to assert the intended production contract.

PWA protection. AASA is a shared web asset; changing it must preserve existing web routes and only add/correct verified app associations. No PWA layout or runtime behavior should change.

Acceptance. A real iPhone opens every allowlisted utahpros.app Universal Link directly into the installed build; invalid paths stay in the browser; credentials association validates; TestFlight signs with the paid team.

### PUSH-01 — Native push is dormant and appointment destinations are not mobile-safe

P0  Evidence: Synthetic delivery not visible + source-confirmed; real APNs/tap pending  ·  Routes: Messages; appointments; Scope Sheet app links

Finding. A simulator APNs payload was accepted by simctl but produced no visible UPR notification, so no notification tap could be exercised. Source confirms APNs enrollment is default-off and the governed dispatcher does not fan out to native device tokens. Appointment notifications also produce only the office route; Field Web Push falls back to /tech and a future native receiver rejects the office path.

Why it happens. Notification events do not use one server-owned destination compiler per audience/platform. A separate APNs endpoint accepts caller-supplied nested data and is not integrated with the event, authorization, retry, idempotency, pruning, and privacy contracts.

Recommended fix. Keep APNs disabled. Add server-owned office, field-PWA, and native destinations for every event; appointment native target is /tech/appointment/:id. Integrate APNs only after authorization, preferences, timeouts, retries, expiry, idempotency, token pruning, and lock-screen content approval are complete.

PWA protection. Retain existing office bell links and correct the already-broken field-PWA appointment fallback. Never use a client-supplied free-form URL as the authoritative destination.

Acceptance. Foreground, background, locked, and terminated taps open the exact permitted thread/appointment for the current account; malformed, stale, cross-account, external, and admin targets fail closed.

## Native surfaces, keyboard, status, and lifecycle

### KB-01 — Capacitor has competing keyboard layout owners

P0  Evidence: Reproduced + source-confirmed  ·  Routes: Messages; Request Signature; appointment forms; every native form with a docked or fixed action

Finding. The software keyboard can cover the Messages composer and consent region. In reproduced Request Signature and appointment forms it also covered the focused fields and all or part of the primary actions. After dismissal, Messages can remain panned so the thread header and Back control are offscreen.

Why it happens. The app forces KeyboardResize.None in configuration and again at runtime, then Messages tries to reconstruct keyboard geometry from visualViewport while sheets and legacy forms rely on ordinary WebView scrolling. There are no native show/hide or app-state listeners that synchronously clear offsets, reveal the focused control and action, and restore the active scroll anchor.

Recommended fix. Create one Capacitor keyboard-layout port. Qualify KeyboardResize.Native or Body on the supported-device matrix, use Capacitor keyboard events and exact keyboardHeight, clear state on willHide/didHide and foreground, then restore the captured focused element and scroll anchor before revealing the WebView.

PWA protection. Keep the existing visualViewport behavior as an independent web/PWA adapter. Native keyboard events and CSS variables must be selected only when Capacitor.isNativePlatform() is true.

Acceptance. Composer, consent banner, attachments, all form fields, and every fixed CTA remain visible; after hide, visualViewport.offsetTop and native lift are zero and the header is reachable. Repeat while backgrounding.
